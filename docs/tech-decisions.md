# 技术选型：为什么这么做

## 1. 为什么语言选 Python（而不是 Go / TS）

Suna 用 Go，是因为它要"单二进制 + 本地 daemon + 强并发 TUI + 跨平台"。
但你现阶段的目标是**最快理解 Agent 原理并跑通链路**，两者目标不同，选型就该不同：

| 需求 | Python 是否满足 | 说明 |
|---|---|---|
| 最快跑通链路 | ✅ | 无编译、代码最短、改完即跑 |
| LLM 生态成熟 | ✅ | OpenAI/Anthropic 官方 SDK 最成熟 |
| 学架构分层 | ✅ | 分层的价值是语言无关的，Python 一样能表达 |
| 单二进制/daemon/TUI | ⚠️ 弱 | 这是 Go 的优势，但**不是第一步要的** |

> 结论：**先用 Python 把一个模块清晰、能跑的 agent 做出来；**
> 如果未来要做成轻量单二进制的本地产品，再补 Go，那时你有架构思路，迁移不痛。

为什么不用 TS/Node：也能做，但对"学分层 + 尽快跑通"这个目标没有 Python 直接。
Node 的优势在于 Web/TUI 事件驱动，属于后话。

## 2. 为什么用 OpenAI SDK，而不是自己拼 HTTP/SSE

- OpenAI SDK 一行代码完成"协议封装、鉴权、错误解析、消息结构化"。
- 手写 SSE 解析 + JSON 边界处理很容易出 bug，是低价值工作，留给 SDK。
- 关键：**SDK 支持传 `base_url`**，所以这一个 SDK 同时能接 OpenAI、DeepSeek、
  本地 vLLM、Ollama。我们不需要为每个厂商写一套请求代码。
- 教训：**别让"厂商适配"侵入核心循环**。我们的 `runner` 只依赖 SDK 的通用形态
  （messages + tools + choices），换模型只需改配置，不需改逻辑。
  （这正是 Suna 用 `model.Adapter` 隔离具体 SDK 的原因。）

## 3. 工具调用为什么要用官方 Function Calling，而不是让模型输出 JSON 文本自己解析

两种做法：
- **（推荐）函数调用 / function calling**：模型原生返回结构化 `tool_calls`，
  我们只需填空执行，协议保证参数是合法 JSON。这是 OpenAI/Anthropic 的标准能力。
- **（不推荐）让模型用自然语言输出 JSON，自己正则/解析**：极不稳定，
  模型会犯语法错、漏引号，你还要自己维护协议。属于"重新发明轮子"。

> 教训：**优先用模型方提供的原生结构化能力，而不是靠提示词 + 自解析。**

## 4. 为什么"记忆"只是一个列表 + 裁剪，不是数据库

- 大模型本身**没有记忆**，你每次调用都要把完整历史重发。
- 所以现阶段"记忆"= 存消息列表 + 决定每次发多少（`memory.py`）。
- 裁剪策略用的是最简单的"保留最近 N 条"。缺点：旧上下文会被粗暴丢掉。
- **这是最值得你后续升级的地方**（见 roadmap.md 的记忆升级），
  升级方向：按 token 数裁剪、对旧消息做摘要压缩、SQLite 长期持久化。
- 为什么现在不上数据库？—— 骨架阶段没有长期存储需求，`YAGNI`（你不会需要它）。

## 5. 配置为什么用环境变量，而不是文件/数据库

- 凭据（API key）必须走环境变量，绝不硬编码，这是安全底线。
- 用环境变量 + `dataclass` 默认值，零依赖、零配置解析代码。
- Suna 用 TOML 文件（因为配置项多且分层）；我们第一步配置就 5 个字段，环境变量足够。
- 需要多配置时再按需升级，不提前引入复杂度。

## 6. 为什么依赖这么少（只有 openai 一个）

这个项目刻意保持"轻量、克制"：
- 除 `openai` 外全部用 Python 标准库（`subprocess`, `json`, `dataclass`）。
- 没引入 Web 框架、ORM、pydantic、click 等。每一行代码你都看得懂、能改。
- **先做对一件事，再往上加**。这是从 Suna 的设计哲学学来的：
  「轻量、克制，不预设复杂工作流」。
