# 日期执行过程：一次工具调用的完整流转

> 场景：用户输入「今天的日期是什么？」，Agent 最终通过工具拿到系统日期并回答。
> 本文梳理从输入到输出的完整代码流转。

## 关键认知

内置工具里**并没有** `date` 这个工具。模型之所以能拿到日期，是因为它调用了
`run_command` 工具，参数是 `date` 命令。这体现了 `run_command` 的威力——
模型可以自由组合任意 shell 命令。

---

## 第 0 步：启动时（`Agent.__init__`）

`cli.py` 创建 `Agent(config)` 时，`agent.py` 做了三件事：

```python
self.memory = Memory(max_history=config.max_history)   # 建记忆
self.memory.add_system(config.system_prompt)           # 塞系统提示词
self.schemas = tools.SCHEMAS                            # 工具声明
```

`tools.SCHEMAS` 来自 `builtin.py`，是把每个 `Tool` 的 `.schema` 提出来。
模型能看到的是**声明**（名字/描述/参数），看不到实现：

```python
SCHEMAS = [tool.schema for tool in TOOLS]
# 例如 run_command 的声明：
# {"type":"function", "function":{
#    "name":"run_command",
#    "description":"在本地执行一条 shell 命令...",
#    "parameters":{"type":"object","properties":{"command":{"type":"string"}},"required":["command"]}
# }}
```

---

## 第 1 步：你输入问题（`Agent.run`）

```python
def run(self, user_input, on_delta=None):
    self.memory.add_user(user_input)          # ① 你的话进历史
    messages = self.memory.snapshot()          # ② 取裁剪后的消息列表
    answer = self.runner.run(messages, self.schemas, on_delta)  # ③ 进核心循环
    self.memory.add_assistant(answer)          # ④ 答案写回历史
    return answer
```

此时 `messages` 是：

```
[system: 系统提示词, user: "今天的日期是什么？"]
```

---

## 第 2 步：核心循环（`Runner.run`）—— 这是心脏

```python
for _ in range(MAX_ITERATIONS):        # 最多 8 轮，防死循环
    result = self._one_call(messages, schemas, on_delta)  # 调模型
    tool_calls = result["tool_calls"]

    if tool_calls:                     # 模型想调工具
        messages.append({"role":"assistant", "content":..., "tool_calls":tool_calls})
        for tc in tool_calls:
            print(f"[工具调用] {name}({args})")
            result_text = self._dispatch(tc)          # 执行工具
            messages.append({"role":"tool", "tool_call_id":tc["id"], "content":result_text})
        continue                        # 带上结果，继续循环
    return content                      # 没工具调用 → 这就是最终答案
```

---

## 第 3 步：模型决定调工具（`_one_call`）

模型看到 `run_command` 的声明，判断「要日期 → 执行 `date` 命令」，
于是返回一个 `tool_calls`：

```json
{
  "id": "call_abc123",
  "type": "function",
  "function": {
    "name": "run_command",
    "arguments": "{\"command\": \"date\"}"
  }
}
```

`_one_call` 把它整理成统一结构返回。因为 CLI 传了 `on_delta`，走的是**流式分支**——
工具调用的 `arguments` 是分片来的，按 `index` 归并拼接。

---

## 第 4 步：执行工具（`_dispatch`）

```python
def _dispatch(self, tc):
    name = tc["function"]["name"]        # "run_command"
    tool = tools.tool_for(name)          # 在 TOOLS 里找到 Tool 对象
    kwargs = json.loads(tc["function"]["arguments"])  # {"command":"date"}
    return tool.run(**kwargs)            # 执行
```

`tool.run()` 在 `base.py` 里：

```python
def run(self, **kwargs):
    result = self.fn(**kwargs)           # 真正执行 _run_command("date")
    return truncate_output(result)       # 过限流闸（500行/50KB）
```

`_run_command` 用 `subprocess.run("date", shell=True)` 拿到系统日期，返回类似：

```
2025年 9月 8日 星期一 13:44:00 CST
```

---

## 第 5 步：结果回填，再调一次模型

工具结果以 `role: "tool"` 塞回消息（必须带 `tool_call_id` 和上一步对上）：

```
[system, user:"今天的日期？", assistant(tool_calls), tool:"2025年 9月 8日..."]
```

`continue` 回到循环顶部，**再调一次模型**。这次模型已经看到日期结果，
不再调工具，直接返回纯文字答案，比如：

> 今天是 2025 年 9 月 8 日，星期一。

---

## 第 6 步：收尾

`Runner.run` 返回答案 → `Agent.run` 把它 `add_assistant` 写回历史 →
`cli.py` 打印出来。

---

## 一句话总结

```
你输入 → 进历史 → 调模型 → 模型说"我要调 run_command(date)"
→ 执行 date 命令 → 结果塞回消息 → 再调模型 → 模型基于结果给最终答案 → 打印
```

**核心思想**：大模型一次只能「想一步」。它先声明要调工具，我们执行，
把结果喂回去，它才能基于结果往下走。这就是 agent 的「模型-工具循环」。

---

## 值得注意的点

- `date` 不是独立工具，而是 `run_command` 的威力体现——模型可以自由组合命令。
- 这也正是 `run_command` 最危险的地方（能执行任意 shell 命令）。
- 代码里已标注 TODO：真实使用要加安全审查（Guard），见 `docs/roadmap.md` 阶段 2。

## 附：调试打印——亲眼看到模型返回的原始结构

在 `Runner.run` 里加一行调试打印，就能看到模型每轮返回的原始结构：

```python
for _ in range(MAX_ITERATIONS):
    result = self._one_call(messages, schemas, on_delta)
    content = result["content"]
    tool_calls = result["tool_calls"]

    # 调试：打印模型这一轮返回的原始结构（含 tool_calls）
    print("\n[DEBUG] 模型本轮返回:", result)
```

真实输出示例（问「今天的日期是什么？」）：

**第一轮返回（模型想调工具）**：

```python
{'content': '',
 'tool_calls': [{'id': 'call_1gu0pdu3',
                 'type': 'function',
                 'function': {'name': 'run_command',
                              'arguments': '{"command":"date"}'}}]}
```

- `content` 是空的（模型没直接说话）
- `tool_calls` 里有一个调用：`run_command`，参数是 `{"command":"date"}`

**第二轮返回（模型给出最终答案）**：

```python
{'content': '今天是 **2026年9月9日，星期三**。',
 'tool_calls': []}
```

- `content` 有内容了（最终答案）
- `tool_calls` 是空列表 `[]` → 循环判定「没有工具调用」，直接返回答案

**结论**：模型会返回 `tool_calls`，但只在它想调工具的那一轮。判断逻辑在 `Runner.run`：

```python
if tool_calls:      # 非空 → 执行工具，继续循环
    ...
    continue
return content      # 空 → 这就是最终答案
```

所以整个对话是**两轮**：
1. 第一轮：模型返回 `tool_calls`（要调 `date`）→ 我们执行
2. 第二轮：模型看到日期结果，返回纯文字答案 → 结束

## 附：澄清「模型」到底指什么

**「模型」就是你对接的 API 服务**——也就是 `.env` 里配置的 `deepseek-v4-flash:0731-cloud`。
整个流程里没有第二个「模型」：

```
你的代码 (runner.py)
   │
   │  HTTP 请求（把消息 + 工具声明发过去）
   ▼
DeepSeek API  ← 这就是「模型」
   │
   │  HTTP 响应（返回 content 和/或 tool_calls）
   ▼
你的代码
```

| 代码里的说法 | 实际是什么 |
|-------------|-----------|
| `self.client.chat.completions.create(...)` | 向 DeepSeek API 发请求 |
| 「模型返回 `tool_calls`」 | DeepSeek 的模型在响应里说「我想调 `run_command`」 |
| 「模型返回 `content`」 | DeepSeek 的模型在响应里给出文字答案 |

**关键点**：「模型决定调工具」这个判断，是 DeepSeek 模型自己做的，不是你的代码做的。
你的代码只是：

1. 把工具声明（`run_command` 长什么样）发给模型
2. 模型看完声明，自己决定「要日期 → 调 `run_command(date)`」
3. 你的代码收到这个决定，才去执行

所以 `[DEBUG]` 打印的 `tool_calls`，就是 **DeepSeek 模型返回的原始响应**，
经过 `_one_call` 整理后的样子。

## 附：模型能不能不调工具、直接返回日期？

**技术上可以，但结果不可靠。** 这正是工具调用机制存在的意义。

### 模型确实可以「直接返回日期」

模型不是被强制必须调工具的。它看到你的问题，有两个选择：

1. **直接回答**：`content: "今天是2026年9月9日"`，`tool_calls: []`
2. **调工具**：`tool_calls: [run_command("date")]`

如果它选 1，你的代码会直接把它的话当答案返回，**根本不会执行任何工具**。
`tool_calls: []` 就代表模型选择了直接回答。

### 但问题是：模型「不知道」今天几号

大模型是**训练出来的**，它的知识有截止日期，它**没有实时时钟**，不知道「现在」是什么时候。
所以如果它直接回答日期，只有两种可能：

- **瞎编（幻觉）**：根据训练数据里的某个日期猜一个，很可能是错的
- **碰巧对**：纯属运气

### 那它为什么这次调了 `date` 工具？

因为工具声明里写了 `run_command` 的描述：

> 「在本地执行一条 shell 命令并返回其输出。当需要运行程序或**查看系统信息**时使用。」

模型「知道」自己不知道当前日期，又看到有个工具能「查看系统信息」，于是判断：
**「要准确日期，我应该调工具，而不是瞎猜。」**

### 核心机制

```
模型自己判断：我该直接答，还是调工具？
        │
        ├── 直接答 → 代码直接返回（可能对，可能幻觉）
        │
        └── 调工具 → 代码执行 → 结果喂回去 → 模型基于真实结果再答
```

**工具调用不是强制流程，而是模型的一个「选择」**。你的代码只是：
- 给模型提供工具这个「选项」
- 模型选了，就执行；没选，就直接返回

### 一个实验

问它一个它肯定知道答案的问题，比如「1+1等于几」，它大概率会直接返回 `2`，
`tool_calls` 为空——因为它不需要工具就能答对。

而「今天的日期」这种**它不知道、但工具能查到**的问题，它才会选择调工具。
这就是 agent 设计的精妙之处：**让模型在「我知道」和「我需要查」之间自己判断**。

## 附：第 5 步既然都知道日期了，为什么还要再调一次模型？

**对于 `date` 这种简单工具，这个质疑完全成立**——原始输出已经能看了，
确实可以省掉这次模型调用。但通用设计选择「再调一次模型」，是因为工具结果**不总是**最终答案。

### 为什么通用设计要再调一次模型

**1. 工具输出是「原始数据」，不是「人话」**

`date` 命令的原始输出是：

```
2026年 9月 9日 星期三 13:44:00 CST
```

模型把它整理成自然语言：

> 今天是 **2026年9月9日，星期三**。

对 `date` 来说差别不大，但想想别的工具：

- `run_command("ls")` 返回一堆文件名，模型要总结「项目里有这些文件」
- `read_file` 返回几百行代码，模型要回答「这段代码做了什么」
- 命令报错了，模型要解释错误、决定下一步

**工具返回的是「事实」，模型负责把它变成「回答」。**

**2. 模型可能需要「连续调多个工具」**

这是循环存在的**真正理由**。比如你问：

> 「列出当前目录，然后读最大的那个文件」

流程是：

```
第1轮：模型调 list_dir → 看到文件列表
第2轮：模型判断哪个最大 → 调 read_file
第3轮：模型基于文件内容 → 给出最终答案
```

如果每调一个工具就直接返回，这个「链式推理」就断了。**循环让模型能基于上一步结果决定下一步。**

**3. 模型要处理「意外情况」**

工具可能失败。比如 `run_command("date")` 报错了，模型需要：
- 看到错误信息
- 决定：重试？换个命令？还是向用户解释？

这些判断都需要模型「看到结果后再想一步」。

### 但直觉是对的——可以优化

对于 `date` 这种「输出即答案」的简单工具，确实存在优化空间。业界有几种做法：

| 方案 | 思路 |
|------|------|
| **直接返回** | 工具输出已经可读，就直接给用户，省一次模型调用 |
| **按工具区分** | 给工具加个标记，比如 `direct_return=True`，简单工具直接返回，复杂工具走模型 |
| **保持现状** | 统一走模型，简单，但多花一次调用（多花点 token 钱） |

### 一句话总结

**工具返回的是「事实」，模型负责把它变成「回答」。** 对 `date` 这种简单工具，
直接返回确实更省；但通用 agent 选择统一走模型，是为了支持**多工具链式推理**和**结果解释**——
这是 agent 真正强大的地方。
